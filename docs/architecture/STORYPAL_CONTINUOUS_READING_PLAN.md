## 1. 本轮要交付什么

读者推进原文并连续讨论时，Agent 能延续对人物、事件和读者解读的理解；只有上下文缺少证据时才查证。不是每轮重新从零搜索，也不是把全书或全量结构化记录放进上下文。

首轮范围锁定三件事：已读故事视图自动注入、讨论状态在会话压缩中保留、按证据缺口查原文／结构历史／前文关联。原有定位、确认、安全边界和 Note 行为保持，口吻与完整产品设计不作为开工门槛。

## 2. 已核对的实现与缺口

- StoryMem 的逐 unit `state_snapshot` 已包含 `characters`、`objects`、`locations`、`plotlines`、`recent`、`backdrop` 和 `backdrop_buffer`。这些是自动抽取的故事视野，不是人工确认事实或完整人物弧光／因果图。
- `state.py` 确定性合并 `entity_updates` 和 `plotline_updates`；近期事件窗口上限为五条，溢出进入背景缓冲，章节末再压缩。必须使用当前边界快照，不能使用 `state_final.json`。
- StoryPal 已有 `story_context(kind=recap|entity|plotline)`。recap 仅回传 backdrop 与 recent；entity／plotline 返回边界内更新历史和当前状态。尚未实现下面所说的自动故事视图。
- 当前运行时注入阅读状态和部分单元已读原文前缀，没有自动注入完整的安全结构化视图。
- Evidence 已包含原文、摘要及人物／地点／术语标签；`context_refs` 尚未随 Evidence 回传。前文关联不能假定已经在线生效。
- nanobot 已有近期历史和替换式压缩摘要。默认压缩模板偏长期保留与任务交接，没有专门规定保留剧情讨论中的观点、修正、问题和证据。

GPT-6 Luna 只读核查：108 条单元；summary、recent_event、state_snapshot 各 108 条非空；人物标签 77 条、地点标签 58 条、术语标签 84 条；entity_updates 103 条非空共 422 项，plotline_updates 82 条共 96 项；context_refs 86 条共 304 项。所有 context_refs 元素均为实体／术语名称字符串，不是 unit_id 边。因此首版只能把它们作为查询／名称导航线索，不能宣称已有父子索引或引用图。degraded=True 为 0。四项结构验证通过不代表语义正确；本次只核查字段、计数与少量快照，逐条语义仍需用例抽查。

## 3. 连续理解的分工

| 层 | 内容 | 更新时机 | 使用方式 |
| --- | --- | --- | --- |
| 已读故事视图 | 当前边界的人物／设定／地点状态、情节线、最近事件与早期背景 | 已确认进度或事实源版本变化 | 后端确定性生成，按预算自动带入，不增加模型调用 |
| 正在讨论的理解 | 用户观点、Agent 暂定解释、依据、反证、尚未解答的问题 | 近期轮次自然积累；压缩时归并 | 当前历史直接可见；压缩后由同一次摘要保留 |
| 可回取证据 | 已读原文、人物／情节线变化历史、前文引用 | 上下文不足或需要核验时 | 主 Agent 按需调用已有工具；引用缺口补接口 |
| 显式阅读手账 | 用户明确要求保存的感受、问题、预测 | 现有显式写入规则 | 跨会话按需读取，不被自动讨论摘要替代 |

故事视图可以帮助延续认知，但抽取误差仍可能存在；争议事实、精确引文和重要因果需要原文核对。人物当前状态不等于历史变化，因果与动机也不能由“先后发生”直接推导。

自动讨论摘要仅是会话工作记忆，不写入 Note，不修改剧情事实源，不擅自向手账新增条目。当前窗口先保证同一会话继续、压缩及重启恢复；新会话自动继承完整讨论的产品行为另列 TODO，不能把会话恢复称为跨会话记忆全部完成。

## 4. 工作包与完成判据

### C1：已读故事视图（先做）

- StoryMem 增加只读公开接口 `get_progressive_view(work_id, max_order)`，返回来源版本、snapshot_order、结构化分组及背景／近期事件；不让 StoryPal 访问 adapter 私有加载函数。新接口归本地协作仓库维护，按既有约定验证后提交／推送。
- StoryPal 新增 `reading_context.py` 纯投影／预算模块，并从 `StoryMemoryService` 接入；`tools.py` 的已有运行时上下文入口注入一次。接口与文件名是本轮拟实施契约。
- 首版预算使用单一估算 Token 上限，默认 1500，不声称已调优。已实现最新事件／背景优先、类别轮流、类内最近更新排序；当前讨论对象优先仍待后续按需查证接入。每项完整保留或丢弃，记录截断诊断，不切断 JSON 或丢掉引用后还保留断言。
- `backdrop_buffer` 用预算容纳，避免章中较早事件既不在 recent 也不在 backdrop。进度不变不重新编码向量，不产生额外 LLM 总结调用。nanobot 现有 RuntimeContextBlock 随消息保存且默认参与模型历史回放，因此需要按 source 的历史投影补丁：旧 `storypal_story_view` 从本轮模型输入移除，仅保留当前视图；磁盘原始记录和其他来源块保留。不能用清空历史、删除工具结果或统一关闭所有 runtime context 达成去重。
- 未确认进度返回无故事视图；部分单元仍只注入已读前缀，结构快照最多到完整已读边界。换作品、来源版本变化、重置后重新生成。无数据明确诊断，不自动退回全书最终状态。
- 完成判据：单元测试验证所有注入项目在边界内、总预算有界、来源可定位；同边界重复调用不累积；更高边界能体现状态变化而非覆盖读者旧观点。

### C2：压缩不断线（随后）

- 沿用 nanobot 既有压缩调用，补充中文共读交接约束，不额外安排每轮抽取模型。再次核对发现 archive 当前直接 render 内置 `agent/consolidator_archive.md`，只有 Dream 已使用工作区覆盖；不能宣称 archive 已有同样入口。需一个小补丁复用 workspace_prompts 的安全读取函数，支持 `prompts/consolidator_archive.md`，无覆盖时回退原模板。PersistedPromptContextResolver 只解决工作区路由，不负责模板覆盖。
- 保留作品与讨论范围、用户当前观点及重要修正、Agent 暂定解释、已查证的原文引用、反证／未解决问题、下一次想继续讨论什么；分清用户观点与文本事实。
- 工具输出只保留用于当前理解的要点、unit／order 引用及结果状态，不复制整段工具 JSON。失败调用不能总结成找到证据；猜测不能因重复或压缩而变成事实。
- 压缩摘要本身不是可机械校验的真值；先做提示组装测试和一组受控压缩前后语义核验。失败沿用既有原始归档兜底；有预算截断时不宣称零遗忘。
- 完成判据：最近讨论可直接续接；受控压缩后仍区分旧猜测、后续修正和待核验内容；重启继续同一会话可恢复。Note 和显式手账没有被自动写入。

### C3：证据回路与 Skill（与 C2 的测试准备并行）

- 不新增 Router 或第二个分析模型。修改检索选择契约：先使用当前片段、故事视图、近期对话／摘要；缺口决定工具，而不是“问动机就必须搜索”。
- 当前状态与变化：`story_context(entity|plotline)`；精确引用或争议核对：`search_story`／`get_story_evidence`；旧观点：近期历史／摘要或显式手账。相关调用不代表必须每轮执行。
- 把 context_refs 的名称字符串以可选元数据接回证据，作为查询扩展或实体导航线索，不猜造 unit_id，也不执行不存在的一跳引用图。名称导航返回的更新历史含已读 unit_id 时，才用现有证据工具回取原文；无匹配则回落普通搜索。自动多跳展开暂缓。
- Skill 首版打包为一份短常驻“连续剧情讨论”，但保留三个明确方法段：连续理解（人物／因果／阶段修正）、事实核验（识别依据缺口并补证据）、手账回看（旧观点与新依据对照）。不是删除后两类设计，也不把 Skill 等同于工具列表；独立拆分与动态加载在此之后评估。Skill 提供方法，安全边界仍由服务端强制执行。
- 完成判据：有足够上下文的追问不重复查同一证据；缺少跨段依据时能回取；故事状态与用户猜测相冲突时不静默替换用户观点。

## 5. 各类数据的覆盖方式

“用上可检索内容”指覆盖真实非空类型，不是强制每轮调用所有工具或把 108 个单元全量注入。

| 数据 | 功能入口 | 验证重点 |
| --- | --- | --- |
| text／summary | 原文证据、摘要候选 | 原文是核验依据，摘要不冒充引文 |
| characters／locations／key_terms | 对象与术语定位、查询改写辅助 | 标签质量与名称匹配，不当成人物关系图 |
| entity_updates | 人物／物件／地点的变化历史 | 初次与当前状态区别，历史引用不越界 |
| plotline_updates | 情节线的展开／推进／收束 | 选对线，不能因最终已关闭提前泄露 |
| recent_event／recent | 当前阅读附近发生什么 | 按 order 去重，累计快照不重复堆积 |
| backdrop／backdrop_buffer | 较早背景与章内溢出事件 | 预算、来源范围、不要遗失章中较早上下文 |
| state_snapshot | 连续故事视图 | 每个阅读边界只用该边界或之前快照 |
| context_refs | 名称导航／查询扩展后回取前文 | 实际为名称字符串，不能冒充 unit 引用图；验证无匹配和回取边界 |
| 用户历史／手账 | 解读的延续与修正 | 观点不是原文事实；自动摘要不等于显式保存 |

当前 schema 没有独立、可靠的“完整关系图／因果图／世界规则图谱”，相关理解从上述状态与原文共同形成；不凭文档名称宣称已具备。

## 6. 《流浪地球》小规模连续验收

先用程序做四条链的输入／边界／引用检查，真实对话先执行一条三轮链，再按坏例扩展，不一开始全量多模型测试。模拟用户 GPT-6 Sol，数据查验 GPT-6 Luna；真实 Chatbot 仍按其自身配置运行。

1. 开篇意象与叙述者感受：以既有 we-0011、R20 锚点构造“困惑 → 暂定理解 → 新段落后的修正”。不能把用户感受当作可检索的客观事实，也不能提前借后文解释。
2. 人物与授课语境：用前期人物出现与后续讲解的已读单元，检查人名／指代衔接、角色功能及先前讨论保留。具体边界与金标在数据核对后冻结，不把人物单次出现伪装为成长弧线。
3. 派别与方案因果：复用 R04／R05，已知证据 we-0019、we-0022。第一轮理解立场，下一轮追问方案代价，再追问已有解释中的缺口；不是每轮重复检索同一组证据。
4. 状态推进与前文联系：复用 R14／R15／R22 的 we-0023、we-0025、we-0026，从计划讲解走到新的已读事件。比较“还未发生／已发生”的阶段理解，检查情节线、对象状态和旧预测不混淆。

覆盖检查另遍历全部 108 个边界，不调用模型；每个非空数据类型至少一个使用用例和一个安全／失效用例。后段数据仅用于隔离的开发测试，不能拿来推进真实用户进度；面向初读用户的文档不列未读结局和标准答案。

原有 `chatbot_tests/story_retrieval_goldens.json` 保留为单次召回基线。新增连续用例记录：前置讨论、已读范围、当前已知解释、实际证据缺口、必要／可选证据、期待的理解增量、禁止结论、允许的工具行为。不给审美和动机解读设唯一标准答案。

## 7. 三个半天的顺序与实验

- 第一半天：数据覆盖清单 + C1 接口／投影／注入与定向测试。交付能观察到的安全故事视图，不以模型会聊天作为完成证明。
- 第二半天：C2 压缩延续 + C3 必要查证和连续讨论 Skill；并行准备四条测试链。优先一个完整连续用例，不同时扩大量工具。
- 第三半天：连续链与受控压缩核验；在固定证据需求上比较原 query／真实 Agent query、现有稀疏／jieba／BGE-M3。结果写 result.md，区分召回覆盖、最终理解质量、工具调用与延迟。12 小时是有效工作目标，不保证压缩语义与多方案实验都一次成功。

时间不足优先完成 C1 + 一条压缩前后链；Reranker、全量 embedding 比较、ANN 与新会话自动讨论继承延期，不挤掉连续理解的最小闭环。

## 8. 用户参与点

无需再确认全部九类场景或给出详细接口设计。首个可体验交付时，请用户在真正已读范围连续聊三轮，核验：AI 是否接住自己的观点、后续讨论是否有新增理解、是否无故反复查证。开发侧负责字段核查、边界测试、检索对照和 trace；效果不足按来源、记忆、推理或表达分别定位。

## 9. 底层衔接与增量重构（2026-10-02 核对补充）

### 自动视图的具体含义

它是每轮模型输入中的内部数据块，不是新的数据库、用户可见摘要、模型生成的人物评价或写入型工具。输入为 ReadingProgressStore 已确认的作品和完整已读顺序；输出为该边界的带版本／来源／质量说明的有界状态投影。部分 unit 的原文前缀沿用 reader.py，完整快照不跟着前缀开放。

链路：ReadingProgressStore → StoryMemoryService → PipelineStoryMemoryBackend → StoryMem 新只读接口 → 已读快照 → reading_context.py 投影 → 现有 RuntimeContextBlock → nanobot 模型上下文。已有 story_context 继续提供按需深入的历史与状态，自动块不包含所有历史更新。后台抽取和前端滚动不在这条链路内。

### 模块责任

| 位置 | 保留／复用 | 本轮增量 |
| --- | --- | --- |
| StoryMem storypipe | 现有切分、顺序抽取、确定性 state 合并、FTS／向量索引 | 不重抽取，不迁移数据库，不把用户观点写进源数据 |
| StoryMem storymemory/adapter.py | 事实源缓存与已有公开查询 | 新只读 progressive view；可选 Evidence 名称线索；保留旧方法返回契约 |
| StoryPal story_memory.py | backend 适配与 service 安全过滤 | 新接口代理、视图边界检查、类型与缺失状态处理 |
| StoryPal reading_context.py（新增） | 无 | 纯函数排序／预算／序列化；不读用户文件、不调用模型、不自行写进度 |
| StoryPal tools.py | 现有工具 schema、读写确认与运行时 provider | 复用同一 service，把视图供给 provider；逐步把投影逻辑移出大 tools.py，不重写工具注册 |
| nanobot runtime_context／历史组装 | 已有来源标记与历史持久化 | 单独替换 storypal_story_view 的模型回放版本；原记录不删除 |
| nanobot memory.py | 归档时机、摘要保存、失败兜底 | 工作区 archive 模板覆盖的小补丁，不引入第二套讨论存储 |
| StoryPal 人格／Skill | 现有 AGENTS 及 nanobot SkillsLoader | 修正有上下文仍强制查原文的规则；一份短连续讨论 Skill 可用 always 模式加载，不重新开放文件工具 |
| 用户 Note／手账／进度 | 现有 owner 隔离、显式写入和持久化 | 首轮不改存储格式，不把自动视图或摘要写成手账 |

### 重构约束与测试

1. 新接口保持向后兼容；旧 recap／entity／plotline 和 Evidence 必需字段不删除。原始快照仍为数据源，视图缓存只是可重建投影。
2. adapter `_units_cache` 目前只按作品缓存，未自动按文件版本失效；新视图不能只返回新哈希但仍读取旧缓存。需检测源文件变化并重载，同版本再复用投影。先做读取前失效，不上文件监听或消息队列。
3. 初版默认按最近事件和最近出现的状态排序，不新增焦点分类器；对话中明确对象可用于已有名称匹配，无法匹配就使用通用视图。算法参数暂不复杂拟合。
4. 服务验证 snapshot_order／last_order、条目内 order 范围、work_id 和缺失格式。实体／情节线历史的当前状态不与未来终态混用；摘要 provenance 应区分快照整体范围与项级可核对引用，不给背景摘要伪造单一证据单元。
5. 两个 nanobot 小补丁必须形成可重放 patch，并验证有覆盖／无覆盖、混合 runtime sources、同进度多轮、换作品／重置与压缩输入。provider 会话缓存需核验是否承接新的消息投影，不能只测网页显示无重复。
6. 分层定向测试：adapter 契约 → service 边界 → 投影预算 → 模型输入／归档模板 → 一条真实连续链。C1 已完成前四层中的输入与历史部分；归档模板及真实连续链仍待实施，不以文档更新计作功能通过。

## 10. 用户讨论、手账与 Note 的补充边界

- 阅读手账现有 `ReadingNotebookStore` 独立持久化为每用户 JSON；按作品和阅读锚点过滤。条目含 reaction／question／prediction、内容、时间与来源会话。当前白名单是 `search_reading_journal` 与 `save_journal_entry`，前者只做可选文本包含过滤并返回最多最近 20 条；没有语义回看，也没有开放手账编辑／删除工具。
- Note 只承载剧情外的交互约定，如“不要替作品硬圆”“先讨论再给结论”。对角色、因果或剧情的认知修正归会话工作记忆／手账，不因名称同为“纠正”就写进 Note。
- 融合通过有来源标记的 Context 加主 Agent 的比较／解释完成：故事材料、近期讨论／压缩摘要、按需取回的手账、Note／人格分开供给。不是让 StoryMem 保存用户解读，也不是把四类文本并成一份事实摘要。手账自动常驻尚未实现；本轮先复用按需读，若三轮链证明断读回顾缺少入口，再评估小预算直接带入。
- 同一会话内已有的判断优先从当前历史获取；跨会话只可回看明确保存的手账／旧显式记忆，不声称能找回所有未保存聊天。旧 `search_memory`／`write_memory` 仍在白名单，与手账有语义重叠；先保留兼容，后续经数据盘点确定迁移，不自动双写或直接删除。
- Skill 是可复用的理解／回应方法；Tool 是受约束的具体访问／写入；Workflow 是执行步骤和触发时机。现有 11 项工具按位置进度 2、剧情证据 3、手账 2、Note 2、旧显式阅读记忆 2 分组。上述分组是设计与说明，当前并未实现动态工具注册。
