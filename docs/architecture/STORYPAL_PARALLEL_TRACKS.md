第一批限定 8～10 个案例：R12／R14／R20／R25／R26／R21／R29，加结构历史与无需检索负例；后续再扩既有 29 条。保留每例 work_id、max_order、可见历史、期望来源／必要单元、反证／未知和“不应检索”的条件。金标支持不同合理解释，不指定唯一文学答案。

## 3. 实验方向与边界

1. 先核验当前实现与数据，建立可复现基线和失败分类；确认模型路径／可加载情况，不把下载计划当成功。
2. Query 单因素：raw_user → 人工改写上界参照 → 真实 Agent 工具 query。真实 query 不读取 gold 答案；已有充分上下文时无 query 是合理行为。
3. 稀疏单因素：bigram OR 基线，jieba＋FTS5 或独立 BM25 原型，必要的 OR／AND／短语策略。记录分词／索引构造，避免把查询改写收益归于分词。
4. 候选融合／排序：FTS5、BGE-M3、RRF；候选数／已读边界／证据预算保持可比，再比较一个 reranker 的收益与延迟。Embedding 第二模型、父子组织与 ANN 延后，不能一次堆全部变量。
5. 输出 Hit／Recall@K、MRR、必要证据联合覆盖、边界违规、P50／P95、模型和候选配置、bad cases。小样本数字不推断普遍显著性；文学理解另评。

真实 Chatbot 调用、原文发送与新增下载在需要时说明范围和预算；上次隔离 2+1 授权已用完，不能复用。先完成无需外发的程序采集／离线回放，未采集真实 query 就明确标缺失，不造数。

## 4. 并行代码、数据与 Git 规则

新会话使用同一项目本地目录，不擅自创建 worktree。避免两个会话争改同文件：

- 算法线优先写 `retrieval_experiments/`、`docs/research/retrieval/`、`chatbot_tests/test_retrieval_experiments_*.py`；独立实验结果写 `docs/research/retrieval/RESULT.md`，独立规划／进度也放该目录。
- 应用线维护 `chatbot/src/storypal_chatbot/`、应用测试、人格／Skill、运行服务、主进度和根 result.md。算法线暂不直接改运行工具描述、默认检索、ContextPacker、Note／手账／进度、应用主文档。
- 现有评测脚本／goldens 先只读，可 import 或复制包装；需要共享字段／生产接口变更先给出具体需求，由应用线接入。不要同时修改金标来让方案通过。
- StoryMem 先只读，算法原型和重建索引放隔离 `.runtime/retrieval-experiments/`，不改正式 data／索引，不改抽取管线。需要线上接口变更时协调后由应用线维护并推送。
- 原文、真实用户会话、配置、模型／生成索引不提交公开仓库；新目录中只放自有代码、人工问题／单元编号、配置模板及不含原文的报告。
- 同一 checkout 的 Git index 共享：显式列出自己文件提交，不用 git add .，不切分支／reset／stash 他人工作；发现别人已暂存时暂停自己的提交并报告。每日开工 fetch 分析更新，脏工作区不盲目 pull。
- 算法线不重启服务、不改模型预设和真实用户状态。数据核验用 GPT-6 Luna；模拟用户用 GPT-6 Sol，少量且有明确行为规范。

## 5. 两线交接

算法报告提供案例契约、失败归因、收益／代价和建议配置，应用线决定是否合入生产，不自动替换基线。应用线提供新的证据／记忆接口契约，算法线可在离线实验中评估；功能可以先使用现有检索，不等算法改进完成。

用户参与：优先体验跨会话“记得我们为什么改变理解”，并判断首回复是否有帮助；不承担全量数据检查。需要额外数据、模型发送授权或产品选择时分别提出，不把所有工作绑成一个阻塞项。
