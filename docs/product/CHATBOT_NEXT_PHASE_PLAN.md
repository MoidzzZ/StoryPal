# StoryPal 后续开发规划（v0.2）

**规划日期：2026-09-05**  
**适用范围：StoryPal Chatbot 与本地 StoryMemory 接入**

## 1. 当前基线

已具备的能力：

- 本地 WebUI、Conda 运行环境与 GPT-5.6 Luna 单模型约束；
- `story_state`、`search_story`、`get_story_evidence` 与显式 Notes；
- 会话级防剧透边界：检索与按 ID 读取均不允许越过 `max_seen_order`；
- BM25/FTS 已接入真实《流浪地球》数据；
- 官方 BGE-M3 与 LanceDB 已验证，24 条中文对话式用例中向量检索前 3 命中率为 95.5%；
- 主 Agent 能直接根据对话改写检索词并调用故事工具；不新增独立 Query Analyzer / Router。

当前限制：线上 `search_story` 仍固定使用 BM25；内置通用 Agent 工具尚未形成严格 allowlist；对话历史只依赖 nanobot 自带 checkpoint 和显式 Notes，尚未有 StoryPal 自己的 HistoryMemory 适配层。

## 2. 总体原则

1. **先验证轨迹，再增加结构。** 不为“可能需要”预先引入 Router、RRF、Skill 或复杂工作流。
2. **故事、对话、用户记忆三层分离。** 故事事实只来自 StoryMemory；会话状态只管理阅读进度；Notes 与 Dream 只处理确认的用户信息。
3. **防剧透优先于召回。** 任意检索策略、降级和融合都必须先通过阅读边界测试。
4. **中文优先。** 用户、模型与维护文案，测试场景和验收结论全部使用中文；仅保留必要技术标识。
5. **接口稳定、实现可替换。** Chatbot 仅依赖协作仓库的 `StoryMemory` 适配器契约，不直接耦合其内部数据结构。

## 3. 阶段一：把故事检索变成可用能力

### 3.1 工具安全收敛（已完成）

**结果：** 已实现并验证，实际陪读会话只接触必需工具。

- [x] 为 Luna 配置并测试工具 allowlist：故事状态、故事检索、证据读取、Notes；不保留通用会话能力。
- [x] 默认禁止 cron、spawn、跨会话消息、目标管理及其他通用 Agent 工作台工具；
- [x] Web 搜索暂不默认开放；待中文现实资料能力进入范围后再单独验收。

**验收：** 每轮 AgentRunner 实际只收到五项白名单工具；完整聊天机器人回归 15 项通过。

### 3.2 向量检索的可控接入

**目标：** 让同一 `search_story` 契约支持 FTS 与 BGE-M3 向量回路。

- 引入显式检索策略配置：`fts`、`vector`；默认策略由评估结论决定，不在工具参数中让模型随意切换；
- 向量模型不可用时，记录可观察降级原因并安全回退 FTS；
- gateway 启动后可选择预热模型，或接受首次检索加载成本；先测内存与首轮等待体验；
- 对协作仓库补充模型 ID、固定 revision、向量维度、归一化方式和索引来源哈希，确保可复现。

**验收：** 同一会话的进度、证据格式、相邻上下文和防剧透行为在两种策略下一致；向量不可用不影响基本陪读。

### 3.3 真实 Agent 轨迹测试

**目标：** 验证主 Agent 的工具选择，而非只验证检索函数。

- 至少收集 10 条真实 Luna 轨迹：事实核对、指代追问、情绪化回顾、无需检索的陪伴、缺少进度、越界追问；
- 每条记录用户原话、会话状态、工具参数、证据单元、最终回答和人工判断；
- 固定至少 5 个失败或边界案例，形成回归测试。

**验收：** Agent 不会为纯情绪表达强行检索；模糊指代无法消解时会澄清；每次剧情事实回答可追溯至已读证据。

## 4. 阶段二：完成检索评估，再决定 RRF

**目标：** 用数据而非直觉选择检索方案。

- 当前 24 条《流浪地球》用例扩展到每部作品至少 20 条，总数不少于 60 条；
- 按明确事实、口语改写、人物关系、事件因果、长程回顾、边界防剧透分类统计；
- 对 FTS、向量和仅在离线评估中启用的 RRF 对比前 1/3/5 命中率、耗时、人工相关性与违规数；
- RRF 仅在对多部作品稳定改善前 3 命中，且零防剧透违规时接入；否则保留向量优先、FTS 降级。

**验收：** 形成版本化评估报告和可复跑命令；不会因单部小说的偶然结果上线融合。

## 5. 阶段三：建立最小对话记忆层

**目标：** 让 Chatbot 记得用户与近期讨论，但不污染故事事实。

- 定义 `HistoryMemory` 适配器，先索引已完成会话摘要与用户明确要回看的对话；
- 先采用 SQLite FTS5 或简单关键词检索，不急于加入第二个向量数据库；
- Notes 继续仅在用户明确要求时写入；Dream 仍只允许更新 `SOUL.md` 与 `USER.md`；
- 增加“我刚才的猜测是什么”“你之前为什么这么说”等真实回忆用例，验证按用户、按会话隔离。

**验收：** Chatbot 能说明记忆来源；没有证据时不会编造；故事检索、历史记忆与 Notes 的来源在回答逻辑中可区分。

## 6. 阶段四：陪读体验与受控扩展

**目标：** 从“工具可用”过渡到“自然陪读”。

- 设计证据驱动的简短回顾：只总结当前进度之前的内容；
- 支持用户预测的显式记录与后续核验；
- 接入中文 Web 搜索抽象，用于现实知识问题，并明确区分虚构设定与现实资料；
- 根据累计轨迹决定是否需要 Story Recap 等 Skill；未出现重复稳定模式前不创建工作流。

**验收：** 回顾、预测核验和现实对照均不泄露后续情节，且能够说明引用来源类型。

## 6.1 初次阅读陪读体验（新增优先级）

在继续扩展检索或长期记忆前，优先完成面向首次读者的最小体验闭环：

- 将作品/章节/段落选择转换为用户可理解的阅读定位，并安全映射到内部阅读边界；
- 依据当前锚点提供短回顾，只覆盖已读范围；
- 新增独立阅读手账，分别保存用户确认的反应、问题与预测，绝不与长期 Notes 混写；
- 预测核验必须由用户主动发起，且只有当前已读证据足够时才回答；
- 用“刚开始、困惑、受触动、提出猜测、数日后回归、试探后续”六类轨迹验收体验。

设计依据与细节见 `CHATBOT_FIRST_READING_EXPERIENCE.md`。这不改变故事事实和防剧透边界，只改善用户与它们互动的方式。
完整抽取数据的可用性审计见 `../research/STORY_UNIT_USABILITY_ANALYSIS_2026-09-06.md`。实现时新增两条前置约束：第一版只允许将阅读边界设在“已完整读完的单元”之后；若要支持读到单元中部，必须另加行/段落锚点。原始抽取标签与摘要只作内部证据，不直接构成用户可浏览的知识卡。
## 7. 协作仓库维护约定

每次开始 StoryMemory 相关工作前：

1. `git pull --ff-only origin main`；
2. 检查新提交对 Adapter、索引元数据、数据格式和检索行为的影响；
3. 保留本地未提交改动，不覆盖协作方修改。

每次修改协作仓库接口后：运行相关测试、`git diff --check`、提交正式代码/测试/设计文档并推送 `origin/main`。模型权重、原文、索引产物、`.env` 和临时探针不提交，除非双方单独确认。

## 8. 当前建议的执行顺序

1. 工具 allowlist；
2. 向量策略配置与 FTS 降级；
3. 10 条真实 Luna 轨迹与 bad-case 记录；
4. 三部作品的检索金标扩展；
5. RRF 离线评估；
6. HistoryMemory 最小实现；
7. 回顾、预测和 Web 等陪读功能。

## 9. 明确暂缓

- 独立 Query Analyzer / Router / State Tracker；
- 未经评估的 RRF 或 reranker；
- 复杂多 Agent、后台心跳和自动任务；
- 将故事资料写入 Dream、Notes 或人格文件；
- 在未取得真实数据前，假设结构化剧情抽取字段稳定可用。
