# 缓存内语境处理与证据打包实验

日期：2026-10-03，规则 cached-frame-pack-v1.1。状态：本包完成，未改应用默认。先更新 PLAN／PROGRESS 登记，再执行 CPU 回放；没有新增模型请求、下载模型、加载 Embedding 或 GPU。

## 样本和对照边界

- 主数据：既有 29 例原话的 Dense Top10 缓存，27 例有必要证据集合。全部案例共同评估，R25／R28 只作重点解释，不作选样门控。
- 真实批次保持为 **5 条首次 search_story query＋1 次零工具暂停**，只有 R14／R25／R26 三例有非空既有金标。P01 不定金标、不进正式排序分母；N01 保持真实 skip，不强制搜索。
- 人工 `gold_rewrite` 缓存标为 `human_gold_rewrite`，只作人工上界，不称真实 Agent 查询。三个 query 来源的候选池不同，不能把跨来源差异归因于同一重排规则。
- 来源 108 单元，SHA-256 `30196aab51d91b5c5b564517d6e3f32933bbf9cc4edcf23dd230cc7a19c83c6b`。现有金标、正式索引、应用文件只读。

本包没有对新查询重新编码或搜索向量索引，只检查**已有候选内**的词项排序与选择。因此无法判断新 query 的 Dense 召回变化，也不是专用神经 reranker 实验。

## 预定查询处理规则

所有配置均冻结每例候选 ID 集合 Top10，重排不能添候选或删除候选；只由 ID 排序决定后续 Top5。

| 配置 | 规则 | 原话实际触发 |
|---|---|---|
| cached_dense | 直接保留缓存 Dense 顺序 | 无 |
| clause_terms | 既有标点／疑问词检测恰好两个子问题；按平均子问题词项覆盖重排 | R12、R25、R26、R28 |
| frame_terms | 同样触发；0.75×子问题覆盖＋0.25×完整原问覆盖，使省略主体、阶段和关系的子问题仍可访问整体词项 | 同上 |
| guard_context_terms | 复用上一权重，过滤纯“我是不是记错了”等元问题，并加入明确给定的对话语境 | R14、R20、R25、R26、R28 |

词项使用现有隔离 jieba 0.42.1，去固定口语／疑问停词；阶段与否定词保留。权重为候选内 `1+ln((N+1)/(df+1))`，覆盖为命中词项权重占查询词项总权重。并列按缓存排名，不看时间先后编号或金标。R14／R20 语境来自既有场景明确给出的上文，不从答案或目标单元构造。

这只是词项近似，没有实体共指模型、阶段关系识别、别名扩展或故事事实补写。完整文本参与特征计算，不能保证它的语义关系也被词项分数保留。guard_context 同时改变门控与语境输入，不能把其差异单独归因于某一项。

### 实现修正记录

初跑保存 `cached-frame-pack-v1.json`。复核发现通用停词表误删“开始／先／后／刚才”等阶段词，违反预登记的阶段保留要求；只修正停词过滤，权重、门控、候选及选择规则均未调参。最终结果另存 `cached-frame-pack-v1_1.json`，初跑保留。初跑 guard_context MRR 0.957，修正后 0.938；报告采用符合输入约束的后者，不选择更好看的数值。

## 固定 query／排序后的打包规则

对每个 query 配置交叉比较三个 packer。每个打包对照共用**同一 query、Top10 排序和 Top5 输入**；上限均为 2400 估算 tokens、最多 4 个单元，使用现有应用 ContextPacker 的内容去重及 token 估算。

1. **production**：原应用最多 3 主证据＋1 同章直接邻接补充。
2. **top4**：原类参数改为 4 主证据＋0 邻接；只取排名前四，不因第五条更相关而回填。
3. **coverage4**：在同一 Top5 内，首位适配预算时保留；再按固定问题及给定语境的新增词项覆盖贪心挑选，平分按原排名，预算内最多四条。最终仍由原类以 4 主证据／0 邻接装包；不按金标选择。

同样的最大单元和 token 上限不表示实际材料长度相同，也不保证多取一段有用。coverage4 是词项互补启发式，不能理解为语义互补已被识别。

## 结果

### 全部 29 例原话

排序指标的正式分母均为 27。候选联合@10 全配置 27/27。

| 查询配置 | 联合@3 | 联合@5 | production 装包联合 | top4 装包联合 | coverage4 装包联合 | 首个必要证据 MRR |
|---|---:|---:|---:|---:|---:|---:|
| 缓存 Dense | 26/27 | 27/27 | 26/27 | 26/27 | 26/27 | 0.895 |
| 朴素子问题词项 | 26/27 | 26/27 | 26/27 | 26/27 | 26/27 | 0.932 |
| 完整问题词项语境 | 26/27 | 26/27 | 26/27 | 26/27 | 26/27 | 0.932 |
| 元问题过滤＋给定语境 | 26/27 | 26/27 | 26/27 | 26/27 | 26/27 | 0.938 |

十二组合的装包相对缓存 Dense 默认均无新增成功、无新增失败，仍只有 R25 未覆盖全部必要材料。MRR 的上升不能写成多证据完整性提升；query 重排反而新增 R25 的 Top5 联合损失。frame_terms 对 clause_terms 的必要集合指标没有增益。本轮不是此前分句后分别重新做 Dense 召回的重复实验，两者候选机制不同。

### R25：最大 4 条或词项互补没有解决早段

必要集合 `{4,26}`。缓存 Top5 `[25,26,7,14,4]`：

| 配置 | 模型材料 ID | 估算 tokens | 早段 4 |
|---|---|---:|---|
| 缓存 Dense＋production | 25、26、7 | 507 | 丢失：第 5，不相邻 |
| 缓存 Dense＋top4 | 25、26、7、14 | 734 | 丢失：仍第 5 |
| 缓存 Dense＋coverage4 | 25、26、7、14 | 734 | 丢失：新增词项未令其被选 |

三种词项重排的 Top5 都变成 `[26,25,7,24,18]`，早段 4 被推到 Top5 外。完整原问的词项保留不等于跨阶段因果已经识别；单纯移除邻接要求或提高到四条主证据，也无法自动保护第五位早段。各配置没有触发 token 超限丢弃，瓶颈仍在排序／选择而非本次 2400 token 容量。

真实 Luna query 缓存 Top5 `[25,26,4,5,8]` 三种打包均保留 `[25,26,4,5]`、788 估算 tokens。它在前一真实批次就补齐证据，本包没有产生新的真实 query 收益，亦不能据此把早段排名改善归因于本轮规则。

### R28：在固定候选内保留目标，不等于修复旧分句路径

缓存 Top5 `[17,42,41,31,30]`，目标 42 第 2。三种词项重排的 Top5 `[42,17,41,26,27]`，目标第 1；production 三主证据均有 42，联合装包继续成功。

此前分别对子问题做 Dense 检索时，目标在融合 Top5 外，装包失败；本轮从完整原问的现成 Top10 开始，候选包含 42。这说明对照必须区分候选生成与候选内排序，不能将本轮保持成功写成“重新检索时的阶段丢失已解决”。整体 frame 权重没有在本例产生超出朴素词项的额外增益。

### 指代与元问题的取舍

- R12 的纯元问题被 guard_context 去除，恢复缓存默认路径；必要 4 仍第 1。
- R20 加明确上文后，必要 11 从第 3 升到第 1，默认装包原本已经成功，没有新增联合覆盖。
- R14 加明确上文后，必要 23 从第 1 降到第 2，21 被升到第 1；装包仍成功，但产生首位退化。因此不能因为总体 MRR 上升就推广无条件语境词项重排。

### 真实 query 与人工上界分开记录

五条真实 query 都是关键词式工具参数，没有触发恰好两句疑问的门控；三个词项查询配置均透传，**不是本轮改写有效的正结果**。三个有既有金标的场景在全部打包配置仍是联合@3／@5／装包 3/3。P01 保持暂定集合，不并入分母；三种打包均未新增 20，仍不能证明完整历史回顾证据充分。

29 例人工改写缓存的默认及其他配置装包联合均为 27/27，查询内重排未改善；它使用人工提供的检索词及另一候选池，只能说明上界差异，不能作为自动算法的成绩。

## 审计、成本与可复现性

- 36 个数据源／排序／打包组合，每轮 756 次缓存装包；所有候选集合保持不变，最多 4 单元、实际最大 1234 估算 tokens、零候选／装包边界越界。
- 用当前应用 packer 对原话默认结果逐例核对：29 例的主＋相邻 ID 顺序及 token 估算均与以前的 Dense 装包缓存一致。真实 query 默认结果也逐例等于实际工具原文集合。
- 执行前后 requests.jsonl SHA 一致。运行进程未导入 torch／sentence_transformers／openai；没有 adapter 搜索、模型调用或 GPU 工作。jieba 词典在 CPU 从已有缓存初始化，约 0.77 秒，不是加载神经模型。
- 缓存 Dense 原话默认打包本地中位 0.134 ms，top4 0.105 ms，coverage4 0.218 ms。这些是缓存词项重排／选择开销，不含原始检索、词典初始化、原文分词或最终回答，不代表服务端到端延迟。coverage4 实际材料有变化，不能把小耗时作为上线理由。
- 定向回归 **27/27** 通过（2.44 秒），新增 6 例覆盖阶段／否定词、语境与元问题、固定候选、第五条选择及 token 上限、缓存哈希／边界／预算和 provisional 分母。测试替身不产生真实模型请求。

代码与复跑入口见 README。忽略目录保存两次报告和 `cached-frame-pack-v1_1.manifest.json`，源缓存、源数据、金标、代码、pack 类及模型账本均留哈希。仓库只收编号／汇总，没有故事原文或模型会话。

## 取舍与下一步

本包不采用这些规则替换生产检索或打包：无装包覆盖收益，词项重排有 R25 Top5 损失及 R14 首位退化。完整问题语境应保留，但简单词项权重不能代表主体、阶段和关系的语义对齐。

后续先登记更明确的阶段与关系约束及其可观察输入，仍需全部开发例的损失审计；独立样本验证前不作应用接入结论。专用神经 reranker 和成对最终回答仍只规划，待新的模型范围／预算授权；本包没有这些结果。P01 先人工明确任务与证据粒度，再规划结构导航与历史材料组织。
